# SDLC 가이드
## 이 프로젝트처럼 기획 → 설계 → 구현 → 산출물을 만드는 방법

> Claude Code에서 `/sdlc` 스킬로 언제든지 실행 가능합니다.

---

## CallBot AutoAudit이 따른 개발 순서

이 프로젝트는 아래 순서로 개발되었습니다:

```
1. 기획서          → docs/1_기획서.md
2. 아키텍처 설계서  → docs/2_아키텍처_설계서.md
3. API 정의서      → docs/3_API_정의서.md
4. 구현            → AutoAudit/app/cp1~cp6/
5. 테스트          → AutoAudit/tests/ (126개)
6. 산출물          → docs/4_상세설명서.md, docs/5_메뉴얼.md
7. 정합성 검토     → 소스 ↔ 문서 19건 수정
```

---

## 새 프로젝트에 적용하기

### 1단계: 스킬 실행

```bash
# Claude Code에서
/sdlc
```

Claude가 다음 질문을 합니다:
1. 프로젝트명은?
2. 해결할 핵심 문제는?
3. 주요 사용자는?
4. 기술 스택 제약은?
5. 일정 제약은?

### 2단계: 템플릿 활용

`~/.claude/skills/sdlc/templates/`의 템플릿을 사용합니다:
- `1_기획서.template.md` → 기획서 초안
- `2_아키텍처_설계서.template.md` → 아키텍처 초안
- `3_API_정의서.template.md` → API 계약 초안
- `4_프로그램_상세_설명서.template.md` → 구현 설명
- `5_사용자_메뉴얼.template.md` → 사용 가이드

### 3단계: 문서 → 코드 순서

**반드시 문서 먼저, 코드 나중에:**

```
기획서로 방향 합의
    ↓
아키텍처로 구조 합의
    ↓
API 정의서로 계약 확정
    ↓
코드 구현 (문서 기반)
    ↓
산출물 문서 (코드 기반)
    ↓
/sdlc review 로 정합성 확인
```

---

## 정합성 유지 원칙

**문서와 소스가 달라지는 순간 신뢰를 잃습니다.**

이를 방지하려면:

```bash
# 소스 변경 후 항상 실행
/sdlc review

# 발견된 불일치를 즉시 수정
# (소스가 맞으면 문서 수정, 문서가 맞으면 소스 수정)
```

### 이 프로젝트에서 발견된 불일치 예시

| 문서 내용 | 실제 소스 | 수정 방향 |
|---------|--------|----------|
| Mock 임베딩 384차원 | `_DIM = 64` | 문서 → 64차원으로 수정 |
| `GeminiProvider` 클래스명 | `GoogleProvider` | 문서 교정 |
| SQLite 3개 테이블 | 실제 5개 테이블 | 문서에 5개 추가 |
| TXT 헤더 `[Call: C001]` | `[CALL_ID: C001] [SUBSCRIBER: S01]` | 문서 교정 |

## Phase별 Claude에게 하는 말

```
Phase 1: "이 요구사항으로 기획서 작성해줘: {요구사항}"
Phase 2: "기획서 보고 아키텍처 설계서 만들어줘. 스택은 {스택}."
Phase 3: "아키텍처 보고 API 정의서 설계해줘."
Phase 4: "API 정의서 기반으로 {엔드포인트} 구현해줘."
Phase 6: "소스 코드 분석해서 프로그램 설명서와 사용자 메뉴얼 작성해줘."
Phase 7: "문서와 소스 코드 비교해서 다른 부분 수정해줘."
```
